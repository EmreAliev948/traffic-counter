# Преброяване на трафика от публични камери (v3)

Курсов проект по „Големи данни“. Системата гледа публични видеопотоци на живо,
разпознава превозни средства и пешеходци, следи всеки обект и брои колко пъти
обектите пресичат виртуална линия – по клас и по посока. Пазят се само
метаданни в SQLite; видео и изображения никога не се записват.

```
камера (HLS / YouTube) ──► OpenCV кадър в RAM ──► YOLO26n (откриване)
     ──► ByteTrack (проследяване, id на обект) ──► пресичане на линия (клас, посока)
     ──► SQLite (събития + състояние на потока) ──► анализ (pandas) ──► Streamlit табло / отчет (PNG, CSV)
```

## Структура

| Файл | Какво прави |
|---|---|
| `config.yaml` | камери (URL, линия за броене) и общи настройки |
| `traffic/config.py` | зарежда и проверява `config.yaml` |
| `traffic/stream.py` | отваря потока (yt-dlp за YouTube), автоматично повторно свързване с нарастващо изчакване 2 s → 60 s |
| `traffic/counter.py` | чиста логика за пресичане на линията (без OpenCV и БД) |
| `traffic/worker.py` | по един процес на камера: кадър → YOLO + ByteTrack → броене → запис в SQLite |
| `traffic/db.py` | схема на SQLite, пакетни записи, заявки |
| `traffic/analysis.py` | анализ: време на работа, честота на час, декомпозиция, аномалии (z-оценка), ден/нощ, делник/почивен ден, прекъсвания |
| `traffic/dashboard.py` | табло със Streamlit |
| `tools/calibrate.py` | избор на линията с два клика върху кадър на живо |
| `tools/manual_counter.py` | ръчно броене с клавиатурата → CSV (еталон) |
| `tools/evaluate.py` | сравнение ръчно vs автоматично броене (един или няколко CSV файла) |
| `tools/report.py` | графики (PNG, matplotlib) и таблици (CSV) за писмената част |
| `tests/` | тестове (без мрежа) |

## Инсталация

Нужен е Python 3.11, 3.12 или 3.13 (за 3.14+ няма PyTorch 2.14.1). Командите се изпълняват от папка `v3`.

```bash
cd v3
python3.13 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt     # за разработка: pip install -r requirements-dev.txt
```

При първото стартиране `ultralytics` изтегля модела `yolo26n.pt` (≈5 MB).
Ако той не може да се зареди, се използва `yolo11n.pt` (`fallback_model`).

## Добавяне на камера и калибриране на линията

1. Добавете запис в `config.yaml`:

   ```yaml
   - id: "20"
     name: София - бул. Пример
     url: https://www.youtube.com/watch?v=XXXXXXXXXXX   # или директен .m3u8 / rtsp://
     enabled: true
     line: [[0, 0], [1, 1]]                             # временно
   ```

   YouTube и други уеб страници се превръщат в директен поток с `yt-dlp`.
   yt-dlp може да предупреди, че липсва JavaScript среда (deno). Потоците на живо
   работят и без нея, но ако YouTube спре да се отваря, инсталирайте `deno` и обновете `yt-dlp`.
   Директни адреси (`.m3u8`, `rtsp://`) се отварят направо.

2. Изберете линията:

   ```bash
   python -m tools.calibrate 20
   ```

   Показва се един кадър (само в паметта). Кликнете началото и края на линията
   напречно на пътя и натиснете Enter. Програмата отпечатва ред `line: [[x1, y1], [x2, y2]]`,
   който копирате в `config.yaml`. Координатите са в пиксели на оригиналната резолюция на потока.

3. **Посока.** Застанете мислено в първата точка и гледайте към втората:
   `in` = обектът минава от лявата към дясната ви страна, `out` = обратното.
   Стрелката „in“ в прозореца показва посоката. За хоризонтална линия, начертана
   отляво надясно, `in` означава движение надолу в кадъра.

## Стартиране

```bash
python -m traffic run                 # всички камери с enabled: true, паралелно
python -m traffic run --only 2,5      # само избрани камери (и изключени)
python -m traffic run --only 2 --preview   # прозорец с рамки и линия (нищо не се записва)
```

Спиране: `Ctrl+C`. Буферираните събития се записват преди изход.
Ако процес на камера умре, главният процес го стартира наново след 10 s.
Ако потокът прекъсне, работникът се свързва отново (2 s, 4 s, … до 60 s) и
взема нов адрес чрез yt-dlp, защото адресите на YouTube изтичат. След повторно
свързване проследяването (ByteTrack) и броячът се нулират: старите позиции вече не
важат и иначе стара следа може да се свърже с нов обект и да даде фалшиво пресичане.
При спиране всеки работник записва състояние `stopped`.

**Производителност.** `vid_stride: 2` анализира всеки втори кадър (25 fps → 12,5 кадъра/s).
Ако компютърът не смогва, увеличете `vid_stride` или намалете `imgsz`.
Процесорните ядра се разделят поравно между камерите. Реалната скорост се записва
на всеки 30 s в таблицата `stream_health` и се вижда в таблото.

## Табло

```bash
python -m traffic dashboard           # отваря http://localhost:8501
```

Филтри по камера, период и граници на „ден“. Раздели (методите от т. 1.5.3 на теоретичната част):

* **Описателна статистика** – общо, по посоки, часове с работещ поток (покритие), средно на час;
  преминавания на час по клас; разпределение по клас и посока.
* **Времеви профил** – топлинна карта час × ден от седмицата.
* **Сравнения** – ден/нощ и делник/почивен ден (средно на час), дял на класовете ден/нощ.
* **Декомпозиция** – тенденция (центрирана 24-часова плъзгаща средна), дневна сезонност,
  седмична сезонност (при ≥ 14 дни данни) и остатък; нужни са ≥ 48 часа с данни.
* **Аномалии** – часове с |z-оценка| ≥ 3 на остатъка.
* **Прекъсвания** – периоди без данни с причина: прекъснат поток, повторно свързване,
  спряна програма или процес, който е спрял да изпраща сигнал.

**Липса на данни ≠ липса на движение.** От `stream_health` се възстановява кога всяка камера
реално е работила (запис `up` на всеки 30 s; ако 90 s няма запис, камерата се счита за
неработеща). Средните стойности са „на час работа на камера“; часове с < 30 минути работа
не получават стойност и се виждат като празни места в графиките, а не като нула.

Таблото отваря базата **само за четене**. Времената в базата са в UTC, а таблото ги
показва в часовата зона от `defaults.timezone`.

## Отчет за писмената част

```bash
python -m traffic report --from 2026-10-20 --to 2026-10-26        # всички камери
python -m traffic report --from 2026-10-20 --to 2026-10-26 --camera 2
```

Записва в `reports/<от>_<до>/` графики (`hourly.png`, `daily_profile.png`, `heatmap.png`,
`classes.png`, `periods.png`, `decomposition.png`), таблици CSV и `summary.txt` с основните
числа. Използва същия анализ като таблото. Рисуват се само агрегирани бройки, не кадри.

## База данни (`data/traffic.db`)

| Таблица | Съдържание |
|---|---|
| `camera` | `camera_id`, `name`, `url`, `line_json` |
| `crossing_event` | `event_id`, `camera_id`, `ts_utc`, `track_id`, `class_name`, `direction`, `confidence` |
| `stream_health` | `camera_id`, `ts_utc`, `status` (`up`/`down`/`reconnecting`/`stopped`), `fps` |
| `traffic_1min` (изглед) | брой на минута по камера, клас и посока |

`event_id` е хеш от камера + стартиране (run id) + номер на връзката + id на обекта + посока и се записва с
`INSERT OR IGNORE`, затова дубликати са невъзможни. Базата работи в режим WAL,
за да пишат няколко процеса едновременно. Пример:

```bash
sqlite3 data/traffic.db "SELECT class_name, direction, SUM(n) FROM traffic_1min GROUP BY 1, 2;"
```

## Оценка на точността

1. Стартирайте `python -m traffic run --only 2` в един терминал.
2. В друг терминал бройте ръчно, докато гледате същата камера:

   ```bash
   python -m tools.manual_counter 2
   ```

   Клавиши: `c` кола, `t` камион, `b` автобус, `m` мотор, `p` пешеходец, `y` велосипед.
   Малка буква = `in`, главна (Shift) = `out`. Backspace = отмяна, `q` = край.
   Записва се само CSV (време, камера, клас, посока). При изход се отпечатва готова команда за оценка.

3. Сравнете:

   ```bash
   python -m tools.evaluate manual/cam2_....csv --start 2026-10-15T08:00:00.000Z --end 2026-10-15T08:15:00.000Z
   ```

   За всеки клас и посока: ръчно, автоматично, абсолютна грешка, % грешка, плюс общата MAE.
   **Критерий за успех:** ≤ 10 % обща грешка за леки коли през деня.

4. Препоръчителен план: по 15 минути на всяка камера през деня и през нощта.
   После сравнете всички наведнъж и запишете обобщена таблица:

   ```bash
   python -m tools.evaluate manual/*.csv --summary reports/accuracy.csv
   ```

Всички команди могат да се извикат и през `python -m traffic calibrate | manual-count | evaluate | report ...`.

## Как работи броенето

* **YOLO26n** открива обектите в кадъра (COCO класове 0, 1, 2, 3, 5, 7).
* **ByteTrack** (вграден в ultralytics) дава постоянен id на всеки обект. Свързването
  става на два етапа: първо с уверените откривания (≥ 0,25), после останалите следи
  се свързват с **по-малко уверените** откривания (0,1–0,25). Така частично закрит обект
  не губи следата си. Затова `conf` на детектора е 0,1: при 0,25 тези откривания биха
  се изхвърлили, преди ByteTrack да ги види. Нова следа пак изисква ≥ 0,25.
* **Пресичане.** За всяка следа се пази предишната долна-средна точка на рамката.
  Пресичане има, когато знакът на векторното произведение спрямо линията се смени
  **и** отсечката на движението реално пресича отсечката на линията. Всеки обект се
  брои най-много веднъж във всяка посока. Следи, невиждани 90 кадъра, се забравят,
  така че паметта остава ограничена при работа 24/7.

## Защита на данните

Системата е проектирана според принципа „защита на данните на етапа на проектиране“
(чл. 25 ОРЗД/GDPR) и минимизация на данните. Тя не извършва биометрична идентификация
(AI Act):

* **Никакво видео или изображение не се записва на диск.** В кода няма `VideoWriter`,
  запис на изображения или кодиране на кадри. Тестът `tests/test_privacy.py` сканира
  целия изходен код и пада, ако такива извиквания се появят. Ultralytics се вика със `save=False`.
* **Кадрите живеят само в RAM** и се освобождават след всяка итерация на цикъла.
  Режимът `--preview` и инструментите показват кадри само на екрана.
* **Без лица, без разпознаване на хора, без регистрационни номера.** Моделът дава
  само клас и рамка. Не се използват библиотеки за лица или OCR (проверява се от теста).
* **Записват се само метаданни:** време (UTC), камера, id на следата (случаен номер,
  валиден само за едно стартиране), клас, посока, увереност.
* Използват се само публично достъпни потоци. Проверете условията за ползване на всеки източник.

## Ограничения

* Публичните потоци се местят или изчезват. Ако камера не работи, сменете URL в `config.yaml`.
* През нощта и при дъжд точността пада. Оценявайте при дневна светлина.
* Времето на събитието е моментът на анализа, който е с няколко секунди (при HLS до
  10–30 s) след реалното събитие, заради буферирането на потока.
* За декомпозиция и аномалии са нужни поне 2 дни непрекъсната работа, а за седмична
  сезонност – поне 2 седмици.
